# 开发流程契约（AI Friends）

> 本文件是本仓库的**强制开发流程**。任何会话、任何 Agent 开工前必须先读。
> 机制层复用 superpowers skills（已安装于 `C:\Users\YGQ\.dsh\skills\`）；本文件补充 superpowers 不管的部分：**用户门禁、改动分级、部署验收**。

---

## 0. 三条铁律

1. **不在 master 上写代码。** 一切改动走 `feature/gqyin/<topic>` 分支 → PR → 合并。
2. **不自己批自己。** 每个门必须用户**明确回复**才算通过。沉默、未回复、"看起来没问题"都不算。不许跨门连做。
3. **没跑过的验证不许说"通过"。** 结论必须附真实命令与真实输出。

---

## 1. 分级：先定档，再走流程

| 档 | 判据（满足一条即封顶该档） | 落盘文档 | 门 |
|---|---|---|---|
| **S** | 单文件、≤30 行、不改接口/DB/可见 UI 结构（文案、样式数值、清晰 bug 修复） | 不需要 | 门 1+2 合并 |
| **M** | 单功能点或单页面、≤5 文件、不跨层 | 不需要（对话里给一页方案） | 门 1 → 2 → 3 → 4 |
| **L** | 跨层（前后端/DB/部署）、多页面、新接口、重构、重做 | spec + plan **必须落盘** | 门 1 → 2 → 3 → 4（文档另走 1~2 轮评审） |

判不准时**往高一级判**。降档必须用户同意。

## 2. 五个阶段 · 四个门

| # | 阶段 | 使用的 skill | 产出 | 用户动作 |
|---|---|---|---|---|
| ① | 澄清需求 | `brainstorming` | 目标 + 验收标准 + 不做什么 | 🚪**门 1** 确认理解 |
| ② | 出方案 | `writing-plans` | 改动清单 + 测试/部署方案 + 风险 | 🚪**门 2** 批准 |
| ③ | 实施 | `using-git-worktrees` → `test-driven-development` | feature 分支 + 提交 + PR | — |
| ③' | 评审 | `requesting-code-review` | 独立 subagent 的 review 报告 | 🚪**门 3** 拍板 |
| ④ | 验收 | `verification-before-completion` | 云端部署 + 证据 | 🚪**门 4** 验收 |
| ⑤ | 收尾 | `finishing-a-development-branch` | 合并 + 清理 | 事后告知 |

**每个阶段开始时必须显式报名** —— `Using [skill] to [purpose]`，让用户看得见当前走在哪套流程上。

### 门 1 · 需求确认（S 档可与门 2 合并成一条消息）

- **目标**：一句话
- **验收标准**：可勾选清单，每条都必须能被命令或截图验证
- **不做什么**：明确划边界
- **分级**：S / M / L

### 门 2 · 方案批准 —— 用户点头前**不许动任何代码**

- **改动清单**：文件级，列具体路径（新增 / 修改 / 删除）
- **关键取舍**：选了什么、为什么、放弃了什么
- **测试方案**：跑什么命令、期望什么输出
- **部署与验收方案**：是否部署、验什么、怎么看
- **风险与回滚**
- **任务拆分**：编号，便于 ③ 逐个执行

> **范围冻结**：门 2 批准后，任何新增的文件、依赖、图标、组件、接口字段都要先问，不许"顺手做了"。

### 门 3 · Code Review

1. 提 PR，取 `BASE_SHA` / `HEAD_SHA`
2. 用 `subagent` 工具派**独立 subagent**（全新上下文，不带本会话历史），按其 `code-reviewer.md` 模板填入改动说明、需求/方案、两个 SHA
3. 结果按 **Critical / Important / Minor** 分级返回
4. Critical 立即修；Important 在 ④ 之前修完；Minor 记录待办
5. 修复后**只重新评审增量**，直到无 Critical / Important
6. 把**结论 + 关键 diff 摘要**交给用户（门 3），由用户拍板

**不许**因为"改动很简单"跳过评审。

### 门 4 · 云端验收

1. 本地构建推送：`ACR_IMAGE=<ACR 公网域名>:latest ./deploy/build.sh`（在 WSL 里跑）
2. 服务器部署：`ssh dsh-aliyun` → `./deploy/server-deploy.sh`
3. 收集证据：镜像 digest、容器状态、`curl -sk https://127.0.0.1/api/health/`、前端资源 hash
4. 交给用户：**可点链接** + **该看什么**
5. 用户说"通过"才算过

> 默认**不**在本地起服务做验收。本地只跑单测与构建。

### ⑤ 收尾清单

- [ ] 合并 PR（用户确认后）
- [ ] 删除远程 + 本地 feature 分支
- [ ] 清理临时文件与测试夹具数据
- [ ] 确认 `git status` 干净（除既有的历史遗留改动）
- [ ] 按需同步文档，并告知用户改了哪些

## 3. 汇报格式（每个门、每次阶段切换都用这个）

```
【阶段】门 N · <阶段名>
【做了什么】<一两句>
【证据】<命令 + 真实输出片段>
【卡在哪】<具体阻塞 / 无>
【等你】<需要用户做的具体决定>
```

**禁止**：连续跨多个阶段不汇报；用"应该没问题""看起来正常"代替证据。

## 4. 文档约定

| 类型 | 路径 | 何时写 |
|---|---|---|
| 设计文档 | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` | L 档 |
| 实施计划 | `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` | L 档 |
| 评审记录 | `docs/superpowers/reviews/YYYY-MM-DD-<topic>-review.md` | L 档 |
| 排障记录 | `docs/troubleshooting/YYYY-MM-DD-<topic>.md` | 按需 |

**修改任何既有文档前，必须先向用户列出"改哪几处、为什么"并获同意。** 不得在实施过程中顺手改文档。

---

## 5. 分支与提交

- 分支名：`feature/gqyin/<topic>`
- 提交信息：中文，`type(scope): 摘要`，例如 `fix(chat): 修正引用角标遮挡`
- 不在 master 上直接提交；不 force push 共享分支
